# 3.2.7.x 개념도/프로세스 보완 장표 선정

## 검토 전제

- `3.2.6 중장년 업무서비스 프로세스`에서 서비스별 대략적인 업무 흐름은 이미 설명한다.
- 따라서 `3.2.7 요구사항별 구현방안`에서는 전체 프로세스를 반복하지 않는다.
- 화면 예시만으로 구현 의도가 약한 장표에 한해 세부 개념도, 상태 전이, 연계 구조, 데이터 산출 구조를 보완한다.
- 목적은 화면 나열을 피하고, 각 요구사항의 구현 방식과 업무 통제 포인트를 명확히 보여주는 것이다.
- 최종적으로 **상세 개념도/프로세스 보완 7개, 약식 기능맵 보완 1개, 화면 중심 유지 6개**로 정리한다.

## 1. 3.2.7.2 전직지원서비스 관리 기능

### 보완 필요성

- 고객이력, 신청·승인, 고객관리, 상담, 재신청예약, 외부일자리·외부훈련이력까지 기능 범위가 넓다.
- 화면만 나열하면 장표가 산만해지고, 전직지원서비스의 핵심인 고객 중심 이력관리 구조가 약해 보인다.
- `3.2.6`에서 전직지원서비스 업무 프로세스를 설명했으므로, 여기서는 프로세스 반복보다 **고객 360도 이력 구조**를 보여주는 것이 적절하다.

### 권장 보완 방식

**고객 360도 이력 구조도**

```text
전직지원 고객
 ├─ 신청/승인 정보
 ├─ 기본정보/고객상태
 ├─ 상담이력/사후상담
 ├─ 교육수료/구직신청/패키지 이력
 ├─ 외부일자리/외부훈련 이력
 └─ 문자·이메일 발송/첨부파일 이력
```

### 장표 구성 방향

- 중앙: 고객 360도 이력 구조도
- 우측 또는 하단: 고객이력 상세 또는 고객 상세 화면 예시
- 하단: 신청·상담·교육·발송·종료·재신청 이력 통합관리 포인트 정리

---

## 2. 3.2.7.8 직업안정 실적관리 기능

### 보완 필요성

- 실적등록, 자동계산, 승인, 예산집행, 교부결정이 연결되는 업무다.
- 단순 화면 예시만으로는 실적 정합성 검증과 승인 통제 구조가 드러나지 않는다.
- `3.2.6`의 직업안정·실적관리 프로세스보다 한 단계 세부적인 **입력·승인·교부결정 흐름**을 보여주는 것이 좋다.

### 권장 보완 방식

**실적 입력·승인·교부결정 세부 흐름도**

```text
기관별 실적 입력
 → 직종/대상 정보 확인
 → 자동계산
 → 임시저장/등록
 → 승인
 → 실적통계 반영
 → 예산집행현황/교부결정보고서 연계
```

### 장표 구성 방향

- 중앙: 실적 입력·승인·교부결정 흐름도
- 우측: 전직지원 실적등록 또는 실적승인 화면 예시
- 하단: 자동계산, 임시저장, 승인, 교부결정 연계 포인트 정리

---

## 3. 3.2.7.10 실적 집계·보고 통계 기능

### 보완 필요성

- 월간/연간 보고서, 요약통계, 정기집계, 수시집계, 집계정보 수정기간이 데이터 마감 흐름과 관련된다.
- 화면 예시만으로는 집계 기준, 수정기간, 확정, 보고서 산출 흐름이 약해진다.
- 이 장표는 단순 통계 조회 화면보다 **집계 마감 프로세스**를 보여줘야 한다.

### 권장 보완 방식

**집계 마감 프로세스**

```text
업무 실적 데이터
 → 정기집계 / 수시집계
 → 집계결과 확인
 → 수정기간 관리
 → 확정
 → 월간·연간 보고서 산출
```

### 장표 구성 방향

- 중앙: 집계 마감 프로세스
- 우측: 정기집계 관리 또는 월간사업실적 화면 예시
- 하단: 정기/수시집계, 수정기간, 보고서 산출, 파일받기 포인트 정리

---

## 4. 3.2.7.11 중장년 공통업무 관리 기능

### 보완 필요성

- 센터정보, 실적목표, 공통코드, 사후서비스 콘텐츠, 강사정보는 각각 독립 화면처럼 보인다.
- 실제로는 교육, 상담, 실적, 지원금, 통계 업무에서 반복 참조되는 기준정보다.
- 화면 예시만 보여주면 단순 등록관리 장표처럼 보이므로, **기준정보 활용 구조도**가 필요하다.

### 권장 보완 방식

**기준정보 활용 구조도**

```text
중장년 공통 기준정보
 ├─ 센터정보 / 운영기관
 ├─ 센터별 실적목표
 ├─ 공통코드 / 코드분류
 ├─ 사후서비스 콘텐츠
 └─ 강사정보
        ↓
교육관리 · 상담관리 · 실적관리 · 지원금관리 · 통계보고에서 참조
```

### 장표 구성 방향

- 중앙: 기준정보 활용 구조도
- 우측: 공통코드 또는 센터정보 관리 화면 예시
- 하단: 기준정보 표준화, 업무 재사용, 통계 일관성 확보 포인트 정리

## 5. 3.2.7.12 경력지원 사업 지원금 지급 관리 기능

### 보완 필요성

- 참여자 자격심사, 참여기업 매칭, 개인지원금 신청·지급, 펌뱅킹 연계, 위탁수수료, 만족도조사, 통계가 연결된다.
- 화면만 보여주면 지원금 업무의 상태 전이와 지급 통제 포인트가 약해진다.
- `3.2.6`에서 지원금 지급 업무 프로세스를 설명했더라도, 여기서는 **경력지원 사업의 세부 지급 상태 전이**를 보여줄 필요가 있다.

### 권장 보완 방식

**지원금 지급 상태 전이도**

```text
참여자 자격심사
 → 승인/반려/보완요청
 → 참여기업 매칭
 → 개인 지원금 신청
 → 지급목록 조회
 → 고용24 펌뱅킹 지급결정
 → 위탁수수료/만족도/통계 반영
```

### 장표 구성 방향

- 중앙: 지원금 지급 상태 전이도
- 우측: 참여자 자격심사 또는 개인 지원금 신청 화면 예시
- 하단: 심사·보완, 매칭, 지급결정, 위탁수수료, 만족도/통계 연계 포인트 정리

---

## 6. 3.2.7.13 일손부족일자리 동행 인센티브 지급 관리 기능

### 보완 필요성

- 참여자 승인, 1차·2차 신청, 펌뱅킹 지급결정, 부정청구 모니터링, 점검표가 이어진다.
- 지급업무는 처리 단계보다 사후점검과 통제 포인트가 중요하다.
- 화면 예시만으로는 1차·2차 지급 구조와 부정청구 모니터링 흐름이 잘 드러나지 않는다.

### 권장 보완 방식

**1차·2차 지급 및 사후점검 흐름도**

```text
참여자 등록/심사
 → 승인/반려/보완
 → 1차 지원금 신청·지급결정
 → 2차 지원금 신청·지급결정
 → 지급현황 관리
 → 부정청구 모니터링
 → 점검표 확인/조치
```

### 장표 구성 방향

- 중앙: 1차·2차 지급 및 사후점검 흐름도
- 우측: 1차/2차 신청 또는 부정청구 모니터링 화면 예시
- 하단: 지급결정, 지급현황, 부정청구, 점검표 관리 포인트 정리

## 7. 3.2.7.14 의사결정용 DW 통계 기반 구축

### 보완 필요성

- 이 장표는 화면 예시보다 데이터 흐름과 통계 활용 구조가 핵심이다.
- 통계 데이터 연동 기반, 통계 테이블 관리, DW/데이터마트 활용, 고용통계분석시스템 기반 조회가 중심이다.
- 화면 예시만 넣으면 구현 의도가 약해지므로 **통계 데이터 연계 구조도**를 중심으로 구성한다.

### 권장 보완 방식

**통계 데이터 연계 구조도**

```text
중장년 업무 데이터
 → 통계 대상 데이터 추출
 → 통계 테이블 생성
 → 데이터 송수신/정합성 검증
 → DW/데이터마트 적재
 → 고용통계분석시스템 조회
 → 정책 의사결정 활용
```

### 장표 구성 방향

- 중앙: 통계 데이터 연계 구조도
- 우측: 주요사업 통계 조회 또는 DW 통계 활용 화면 예시
- 하단: 통계 테이블 생성, 정합성 검증, DW/데이터마트 연계, 정책 의사결정 활용 포인트 정리

## 8. 3.2.7.4 전직지원 기타 관리 기능

### 보완 필요성

- NJRTⅡ 검사, SMS/E-mail 발송, 서비스현황·분석 통계가 서로 성격이 다르다.
- 하나의 업무 프로세스로 묶기에는 무리가 있다.
- 상세 프로세스보다 **상담지원 / 발송지원 / 분석지원** 3개 보조 기능으로 묶어 설명하는 편이 적절하다.

### 권장 보완 방식

**검사·발송·통계 지원기능 맵**

```text
전직지원 기타 관리
 ├─ 상담지원: NJRTⅡ 검사 실시·결과조회·결과통계
 ├─ 발송지원: SMS·E-mail 대상관리·내용등록·발송이력
 └─ 분석지원: 서비스현황·신청/상담/교육·성별/연령별 분석
```

### 장표 구성 방향

- 중앙: 3분할 기능맵
- 우측 또는 하단: SMS·이메일 발송관리 또는 검사 결과조회 화면 예시
- 하단: 검사, 발송, 통계가 전직지원 업무를 보조하는 기능임을 정리

## 최종 적용 기준

### 상세 보완 기준

다음 중 하나에 해당하면 상세 개념도/프로세스를 적용한다.

- 고객 중심으로 여러 이력이 통합되는 경우
- 승인·반려·보완 같은 상태 전이가 중요한 경우
- 지급, 펌뱅킹, 사후점검 등 통제 흐름이 필요한 경우
- 정기집계, 수시집계, 수정기간, 확정 등 마감 흐름이 있는 경우
- 기준정보가 여러 업무에서 참조되는 경우
- DW/통계 데이터 연계처럼 화면보다 데이터 흐름이 중요한 경우

### 약식 보완 기준

다음에 해당하면 상세 프로세스가 아니라 기능맵으로만 보완한다.

- 하나의 연속 업무 흐름이 아닌 보조 기능 묶음인 경우
- 화면 예시는 필요하지만, 기능 간 관계만 간단히 설명하면 되는 경우
- `3.2.6` 프로세스와 중복될 가능성이 큰 경우

### 화면 중심 기준

다음에 해당하면 화면 예시 중심으로 유지한다.

- 단순 조회·검색·파일받기 중심인 경우
- 대시보드 화면 자체가 핵심인 경우
- 이미 `3.2.6`에서 업무 흐름을 충분히 설명한 경우
- 화면 1~2개로 기능 범위가 명확히 전달되는 경우

## 장표 구성 예시

### 상세 개념도/프로세스 보완형

```text
상단 메시지
- 구현 목적과 업무 효과를 1~2문장으로 설명

중앙 콘텐츠
- 좌측: 개념도/프로세스/상태 전이도
- 우측: 대표 화면 예시 1개

하단 구현 포인트
- 핵심 기능 3개 내외
- 연계/검증/승인/통계 처리 포인트 중심
```

### 약식 기능맵 보완형

```text
상단 메시지
- 해당 기능군의 역할을 1문장으로 설명

중앙 콘텐츠
- 3개 내외 기능카드 또는 기능맵
- 필요한 경우 대표 화면 1개 보조 배치

하단 구현 포인트
- 각 기능카드별 핵심 기능 1개씩 정리
```

### 화면 중심형

```text
상단 메시지
- 화면을 통해 처리할 수 있는 업무 효과 설명

중앙 콘텐츠
- 대표 화면 1개 또는 연계 화면 2개

하단 구현 포인트
- 검색, 조회, 등록, 수정, 출력, 파일받기 등 핵심 기능 정리
```

## 최종 결론

- `3.2.7.x`에서는 화면 예시만 계속 나열하지 않되, `3.2.6`의 업무 프로세스를 반복하지 않는다.
- 상세 보완 대상 7개는 화면보다 구조·상태·연계·통제 흐름이 중요하므로 개념도/프로세스를 반드시 포함한다.
- `3.2.7.4`는 상세 프로세스가 아니라 보조 기능맵으로만 보완한다.
