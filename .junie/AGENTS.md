# Junie 작업 가이드라인

## 1. 목적

본 가이드라인은 `중장년내일센터 업무시스템 고용24 행정포털 통합 재구축 사업` 제안 프로젝트에서 Junie를 활용해 제안서 작성, 요구사항 분석, 장표 구성, 변경이력 관리 작업을 일관되게 수행하기 위한 기준을 정의한다.

Junie는 단순 문서 작성 보조 도구가 아니라, 제안 작업자가 정리한 방향을 기준으로 반복 작업을 빠르게 수행하는 실행 보조 도구로 활용한다.

---

## 2. 기본 원칙

### 2.1 사람 주도, AI 보조

- 제안 전략, 핵심 메시지, 최종 표현은 사람이 결정한다.
- Junie는 초안 작성, 목차 정리, 문장 다듬기, 표 변환, 변경사항 정리 등 반복 작업을 지원한다.
- Junie가 생성한 결과는 반드시 사람이 검토한 뒤 반영한다.

### 2.2 근거 기반 작성

- 제안요청서, ISP, 요구사항 정리 문서, 회의 메모 등 제공된 근거를 우선 사용한다.
- 근거가 불명확한 내용은 단정하지 않고 `검토 필요`로 표시한다.
- 요구사항 번호가 있는 경우 가능한 한 함께 표시한다.

### 2.3 짧고 명확한 산출물

- 제안서 문장은 장표에 바로 넣을 수 있도록 짧고 명확하게 작성한다.
- 장표용 문장은 긴 설명문보다 핵심 메시지, 목록, 표 중심으로 정리한다.
- 한 문장에 여러 메시지를 넣지 않는다.

### 2.4 기존 작성 방향 유지

- 이미 확정한 목차, 용어, 표현 방향을 임의로 변경하지 않는다.
- 변경이 필요한 경우 변경 사유를 함께 제시한다.
- 같은 의미의 용어는 프로젝트 내에서 일관되게 사용한다.

## 3. 작업 폴더 기준

Junie 작업은 아래 폴더 구조를 기준으로 수행한다.

```text
proposal-keis-middleaged/
├─ 01_rfp/
├─ 02_analysis/
├─ 03_contents/
├─ 04_images/
├─ 05_ppt/
└─ 06_excel/
```

### 3.1 폴더별 역할

| 폴더 | 용도 |
|---|---|
| `01_rfp/` | 제안요청서, ISP, 원본 참고자료 보관 |
| `02_analysis/` | 요구사항 분석, 업무 프로세스 정리, 기능 매핑 |
| `03_contents/` | 제안서 본문 초안, 장표별 문구, 목차 구성 |
| `04_images/` | 다이어그램, 프로세스 이미지, 화면 예시 이미지 |
| `05_ppt/` | PPT 작업본, 검토본, 최종본, 변경이력 관련 파일 |
| `06_excel/` | 요구사항 매핑표, 변경이력, 산출물 목록 |

## 4. Junie에게 작업 지시하는 방식

### 4.1 좋은 지시 방식

Junie에게는 아래 정보를 함께 제공한다.

- 작업 대상 파일 또는 폴더
- 수정할 범위
- 원하는 결과 형식
- 유지해야 할 표현 방식
- 변경하지 말아야 할 내용

예시:

```text
03_contents/3장_기술및기능.md 파일에서 2.5 서비스 영역별 업무 프로세스 부분만 수정해줘.
장표 제목, 콘텐츠 제목 바, 요구사항 번호, 본문 섹션 헤더 형식은 유지하고,
전직지원서비스/전직지원교육/생애경력설계/기업서비스/직업안정/지원금 순서로 정리해줘.
```

### 4.2 피해야 할 지시 방식

아래처럼 범위가 불명확한 지시는 피한다.

```text
전체적으로 좋게 고쳐줘.
```

```text
제안서 느낌 나게 바꿔줘.
```

```text
알아서 정리해줘.
```

## 5. 문서 작성 규칙

### 5.1 Markdown 우선 작성

- 초안은 가능한 한 Markdown으로 작성한다.
- PPT 반영 전에는 Markdown에서 구조와 메시지를 먼저 확정한다.
- 장표 단위 문서는 제목, 메시지, 구성 요소, 본문 문구를 분리해서 작성한다.

### 5.2 장표 문구 작성 방식

장표 문구는 아래 구조를 우선 사용한다.

```text
장표 제목:
콘텐츠 제목 바:
장표 메시지:
주요 구성:
-
-
-
하단 키포인트:
```

### 5.3 표 작성 방식

- 비교, 매핑, 기능 목록은 표로 정리한다.
- 표 컬럼은 4~6개 이내로 유지한다.
- 셀 안의 문장은 가능한 한 짧게 작성한다.

## 6. 제안서 작성 기준

### 6.1 핵심 표현 방향

본 프로젝트에서는 아래 표현 방향을 우선 적용한다.

- 고용24 행정포털 중심 통합
- 중장년 업무서비스 전면 재구축
- 대민·행정 공통 업무 로직 확보
- 고용24 공통서비스 활용
- 업무 프로세스 기반 기능 구현
- 고객이력 중심 One-screen 업무처리
- 서비스/API 기반 업무서비스 전환
- 데이터 연속성과 업무 안정성 확보

### 6.2 피해야 할 표현

- 근거 없는 과도한 AI/신기술 강조
- RFP에 없는 기능을 확정된 범위처럼 표현
- 기존 시스템을 부정적으로만 표현
- “완벽히”, “무조건”, “전부” 같은 과장 표현
- 발주기관이 정한 용어를 임의로 바꾼 표현

## 7. 요구사항 정리 규칙

### 7.1 요구사항 번호 유지

- 기능 요구사항은 가능한 한 `SFR-001` 형식의 요구사항 번호를 유지한다.
- 보안, 데이터, 제약사항도 각각 `SER`, `DAR`, `COR` 번호를 함께 관리한다.
- 요구사항 번호를 모르는 경우 `요구사항 확인 필요`로 표시한다.

### 7.2 요구사항 매핑 형식

요구사항 정리는 아래 형식을 기본으로 한다.

| 요구사항 번호 | 요구사항 명칭 | 구현 방향 | 장표 반영 위치 | 비고 |
|---|---|---|---|---|
| SFR-003 | 전직지원서비스 관리기능 | 신청, 상담, 종료, 재신청 흐름 중심 구현 | 2.5, 2.8 | 고객이력 중심 |

## 8. PPT 작업 규칙

### 8.1 PPT 직접 수정 전 확인

- PPT에 바로 반영하기 전에 Markdown 초안을 먼저 만든다.
- 장표 메시지와 도식 구성이 확정된 뒤 PPT로 옮긴다.
- PPT 이미지는 가능한 한 편집 가능한 도형 구조를 우선한다.

### 8.2 이미지/도식 작업 기준

- 업무 프로세스는 너무 많은 박스와 화살표를 피한다.
- 핵심 흐름은 진한 색 또는 강조선으로 구분한다.
- 보조 흐름은 얇은 선, 작은 박스, 보조 설명으로 처리한다.
- 장표 내 텍스트는 발표자가 읽을 수 있는 크기를 유지한다.

## 9. 변경이력 관리 규칙

### 9.1 파일 버전 기준

- 파일명에 `_v0.1`, `_v0.2`, `_v0.3`, `_v1.0` 형식의 버전을 사용한다.
- 낮은 버전은 이전본, 높은 버전은 현재본으로 본다.
- 현재본 기준으로 변경이력을 작성한다.

### 9.2 변경 유형

변경이력 유형은 아래 기준을 사용한다.

| 유형 | 설명 |
|---|---|
| 신규 | 새 장표 또는 새 문단 추가 |
| 삭제 | 기존 장표 또는 문단 삭제 |
| 추가 | 기존 장표 내 내용 추가 |
| 문구수정 | 의미 또는 표현 변경 |
| 오탈자수정 | 단순 오탈자, 띄어쓰기 수정 |
| 번호수정 | 목차 번호, 장표 번호 수정 |
| 검토필요 | 변경 여부 판단이 애매한 항목 |

## 11. Junie 작업 프롬프트 템플릿

### 11.1 장표 초안 작성

```text
다음 내용을 기준으로 제안서 장표 초안을 작성해줘.

작업 대상:
주제:
요구사항 번호:
장표 목적:
반드시 포함할 내용:
제외할 내용:
결과 형식:
- 장표 제목
- 콘텐츠 제목 바
- 장표 메시지
- 주요 구성
- 하단 키포인트
```

### 11.2 요구사항 분석

```text
다음 요구사항을 기준으로 제안서 반영 내용을 정리해줘.

요구사항 번호:
요구사항 명칭:
요구사항 원문:

결과는 아래 표로 작성해줘.
- 요구사항 해석
- 구현 방향
- 장표 반영 위치
- 제안 포인트
- 검토 필요 사항
```

### 11.3 문장 다듬기

```text
아래 문장을 제안서 장표에 넣기 좋게 다듬어줘.
문장은 짧게 유지하고, 과장 표현은 제거해줘.
의미는 바꾸지 말고 2~3개 대안으로 제시해줘.

문장:
```

### 11.4 변경이력 작성

```text
이전본과 현재본의 차이를 비교해서 변경이력을 작성해줘.

기준:
- 장표 번호 기준으로 비교
- 변경 유형은 신규/삭제/추가/문구수정/오탈자수정/번호수정/검토필요 중 선택
- 변경 내용은 한 줄로 간결하게 작성
- 판단이 애매하면 검토필요로 표시
```

## 12. 최종 원칙

Junie는 제안 작업을 대신 결정하는 도구가 아니라, 사람이 정한 방향을 빠르게 문서화하고 반복 작업을 줄이는 도구로 사용한다.

따라서 모든 작업은 `근거 확인 → 초안 생성 → 사람 검토 → 반영 → 변경이력 관리` 순서로 수행한다.
